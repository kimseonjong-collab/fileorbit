# FileOrbit V0.5 Development Baseline

V0.4.0 is the immutable stable safety baseline. V0.5 work must preserve its read-only-first, explicit-approval, no-delete, no-overwrite, journaled Move/Undo contract unless a future acceptance document explicitly changes that contract.

## First V0.5 tranche

- [x] History diagnostics: make interrupted/planned-only transactions and journal growth state easier to understand without changing files.
- [x] Review ergonomics: improve explanation of why a download is Recommended / Review / Hold and what user action changes the outcome.
- [x] Folder Map diagnostics: surface ambiguous roles and multi-source roles before Downloads routing.
- [x] Journal maintenance design: explicit export/archive must be copy-only and user-initiated; the live journal is never deleted, truncated, rotated, or compacted by export. Any future compaction requires a separate acceptance change.
- [x] Performance guardrails: retain single-pass History aggregation and transaction-scoped journal validation. CI already exercises a 15,000-record / 200-transaction aggregation regression and must preserve this test before optimization changes.
- [x] Stable compatibility: V0.4 journal records and saved Folder Map data remain readable by V0.5.

## Out of scope until separately approved

- Automatic/background file moves
- File deletion
- Silent overwrite or conflict replacement
- Automatic journal deletion/compaction
- Cloud upload/sync
- Moving files outside the approved Folder Map

## Implemented baseline

- History labels planned-only records as incomplete/review-required instead of implying a completed failure state.
- Downloads explains Recommended / Review / Hold actions and warns when approved Folder Map roles have multiple source folders, so automatic routing stays fail-closed.
- Rust regression coverage loads a V0.4-shaped JSONL journal record to protect backward readability.

## Journal export/archive contract

1. Export is an explicit user action and copies the complete validated JSONL journal to a user-selected destination.
2. Export performs strict journal validation before copying. Interior corruption fails closed; export never repairs or mutates the live journal.
3. Export never deletes, truncates, rotates, compacts, or replaces the live journal.
4. Existing destination files are not silently overwritten.
5. Export is not a backup scheduler and does not run in the background.
6. A later archive/compaction feature must have its own acceptance criteria, recovery story, and Windows runtime checkpoint before it can modify the live journal.

## V0.5 tranche checkpoint

The first V0.5 tranche is intentionally diagnostic/read-only around existing V0.4 safety behavior. No new automatic file mutation path is introduced.

## Journal export implementation

- [x] History UI provides an explicit `Journal 내보내기` action only when records exist.
- [x] Backend validates the complete live journal before export and holds the same journal mutation lock used by Move/Undo/History reads.
- [x] Export uses copy-only semantics, verifies copied byte count, refuses an existing destination, and leaves the live journal byte-for-byte unchanged.
- [x] Regression tests cover successful copy, existing-destination refusal, and corrupt-source fail-closed behavior.
- [x] Web Preview cannot invoke local Journal export.

### Export hardening checkpoint

- [x] Export canonicalizes the live journal and destination parent before comparing the final path, preventing same-file export through path aliases such as `.` segments.
- [x] Export success is presented as a non-error notice; failures remain in the error channel.

### Export verification completion

- [x] Exported copies are strict-read again after the byte-count check. If the copied JSONL cannot be parsed under the same journal rules, the copy is removed and export fails.
- [x] Successful export feedback includes the selected destination, copied size, and explicit copy revalidation status.

The first V0.5 tranche is now source-complete. A Windows checkpoint is intentionally deferred until another user-visible V0.5 feature justifies batching runtime validation.

## Folder Map routing diagnostics completion

- [x] Routing readiness is now shown on the Folder Map itself before approval: roles with exactly one source folder are marked automatic-routing ready; multi-folder roles are marked limited.
- [x] The recommended-structure approval view repeats the automatic-destination readiness summary and explains that approval remains allowed while ambiguous roles stay fail-closed in Downloads.
- [x] These diagnostics are read-only and do not change V0.4 Move eligibility or backend validation.

## Downloads review-state clarity

- [x] Queue summary distinguishes automatic recommendation counts from explicit user-approved files.
- [x] Every destination row states whether it is user-approved, held, or undecided; automatic recommendation alone never implies Move approval.
- [x] Changing a file's role clears its prior user decision and invalidates backend validation / final Move arming.
- [x] Every Downloads rescan invalidates backend validation / final Move arming and prunes decisions and role overrides for files no longer present.
- [x] Move Gate text explicitly states that only user-approved files participate and that changed classification, destination, or rescan requires backend revalidation.

## Destination-conflict preflight

- [x] Downloads detects case-insensitive duplicate target paths before backend Move validation and shows the conflict count in the queue summary.
- [x] Conflicting rows explain that multiple source files resolve to the same destination and disable new approval.
- [x] A previously approved row that later becomes conflicting is excluded from the effective approved Move set and is explicitly labelled as excluded.
- [x] Backend duplicate-target validation remains authoritative; the UI check is an earlier usability/safety diagnostic, not a replacement.

## Windows path identity hardening

- [x] UI duplicate-target preflight folds path case and trims trailing spaces/dots from each Windows path segment before comparing target identities.
- [x] Backend duplicate-target validation uses the same Windows identity principle, while non-Windows validation preserves native path identity.
- [x] Canonical approved-root containment and existing-destination checks remain authoritative after duplicate-plan detection.

## Windows invalid-name guard

- [x] Backend rejects Windows reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`) and target segments ending in spaces/dots before Move.
- [x] Downloads surfaces the same invalid-target condition, counts it separately, disables approval, and excludes any previously approved invalid target from the effective Move set.
- [x] Existing backend containment, collision, and snapshot validation remain mandatory after this earlier name check.

### Windows invalid-character completion

- [x] Destination segments containing Windows-invalid filename characters (`< > : \" | ? *` or control characters) are rejected before Move; the drive designator remains valid.
- [x] Downloads applies the same early diagnostic and excludes invalid destinations from effective approval.
- [x] Backend validation remains the final authority even when the UI preflight has already blocked the row.

## Execution-time destination revalidation

- [x] Windows destination-name safety is rechecked immediately before each physical Move, not only during the earlier validation command.
- [x] The execution-time target guard centralizes relative-path, Windows invalid-name, approved-root containment, and existing-destination checks.
- [x] Regression coverage proves existing destinations and parent-directory traversal fail the execution guard while a new approved descendant remains eligible.
- [x] No arbitrary legacy `MAX_PATH=260` rejection was introduced; path-length behavior remains delegated to the actual Windows/Tauri filesystem environment rather than imposing a potentially incorrect application limit.

## Move/Undo TOCTOU hardening

- [x] Target-parent creation is centralized and followed immediately by canonical approved-root containment revalidation plus an existing-target recheck.
- [x] Regression tests cover newly created approved descendants and refusal to overwrite a target that appears before execution.
- [x] Undo now reapplies current relative-path and Windows destination-name safety rules to the recorded original path before recreating/restoring it.
- [x] These checks complement, rather than replace, journal integrity and physical Move/Undo compensation safeguards.

## Undo journal-transition integrity

- [x] Undo requires each actionable `moved/undone/undo_failed` transition to match an earlier `planned` record for the same transaction/source/target.
- [x] A changed target or a transition without a planned predecessor fails closed before Undo mutates files.
- [x] Strict transition validation is intentionally scoped to Undo. General journal reading, History, export, and V0.4-shaped records retain backward-compatible partial-history readability.
