# FileOrbit V0.4 Acceptance

## Release gate
V0.4 is acceptable for a Windows checkpoint build only when all items below pass.

### Folder Doctor / Folder Map
- [x] Existing work root is selected explicitly by the user. (desktop folder dialog; Work Root is separate from Downloads Root)
- [x] Folder scan is read-only. (backend scan path performs metadata/read traversal only; no mutation calls)
- [x] Noise exclusions do not mutate disk content. (excluded directories are skipped by WalkDir filter only)
- [x] Folder Map is persisted only after explicit approval. (`fileorbit.folderMap.v02` is written by the explicit approval action)
- [x] Drift between saved Folder Map sources and a later scan is visible. (saved/current source sets show added/missing counts)

### Downloads Organizer
- [x] Downloads root is selected explicitly. (desktop UI keeps Downloads selection separate from Folder Map work root; UI and Rust reject either root being equal to or nested inside the other)
- [x] Scanning does not move, rename, delete, or overwrite files. (`scan_downloads` reads directory entries/metadata only)
- [x] Recommendation, review, and hold states are distinguishable. (separate counts, filters, status labels, and confidence treatment)
- [x] Manual classification correction is stored locally. (role overrides + learned filename tokens persist locally and are scoped to the approved map)
- [x] Per-file review decisions and overrides are scoped to Folder Map approval version + Folder Map root + Downloads root. Re-approving a Folder Map invalidates prior approvals so a changed destination map cannot inherit stale Move approval.
- [x] Re-scan retains decisions only for files still present. (scan reconciliation prunes stale decision/override keys)
- [x] Downloads recommendations route only to an actually approved Folder Map source folder. A role with multiple approved source folders is held for review instead of synthesizing a new destination directory.

### Move safety
- [x] Move requires approved Folder Map. (UI gate + backend approved-root validation)
- [x] Move requires explicit per-file approval and final Move confirmation. (desktop Move Gate; changing approval/classification or re-scanning invalidates the prior validation/armed state)
- [x] Rust validates source under selected Downloads root. (preflight + execution-time canonical-path guard)
- [x] Rust validates target under approved work root using the canonicalized existing target parent. This avoids Windows `\\?\\C:\\...` canonical-prefix false negatives while retaining symlink/escape containment.
- [x] Parent-directory traversal and invalid relative path elements are rejected. (backend guard + Rust unit test)
- [x] Existing destination collision is rejected; overwrite is never silent. (preflight immutability regression + move primitive guard)
- [x] Duplicate source or duplicate target entries in one Move plan are rejected before execution. Source identity is canonicalized; Windows duplicate comparison is case-insensitive.
- [x] Same-volume move is journaled. (`planned` then `moved`/`failed` entries are appended around execution)
- [x] Cross-volume fallback uses temporary copy + byte-size verification before source removal. (forced fallback Rust unit test)
- [x] Failed cross-volume source removal attempts rollback of the created destination. (fallback implementation removes created target if source removal fails; controlled failure injection remains optional)

### Journal / Undo
- [x] Planned, moved, failed, undone, and undo_failed states are auditable in the JSONL journal; execution-time Move failures are journaled after `planned`.
- [x] Move history is persisted in the app-data JSONL journal and reloaded after restart; each appended record is flushed with `sync_data` before it is treated as committed.
- [x] Undo availability is derived from the latest successful moved/undone state per source.
- [x] Undo collision stops that item rather than overwriting the original path. (undo precheck Rust unit test)
- [x] Failed Undo remains retryable after the external cause is resolved. (backend state remains undoable and desktop UI retains the failed last transaction for retry)
- [x] Empty, unknown, or fully exhausted Undo transactions do not report a false success; backend returns an explicit error.
- [x] Transaction detail exposes source, target, status, and error.

### Build / regression
- [x] Frontend build passes. (CI run 36212281162, 2026-09-26)
- [x] Rust/Tauri CI including cargo test passes. (run 36212281162)
- [x] Web Preview build passes. (run 36212281147)
- [x] Web Preview clearly states that it uses demo data.
- [x] Desktop safety copy describes V0.4 explicit Safe Move/Undo, not V0.1 read-only behavior.
- [x] Windows installer is generated only at an explicit checkpoint request.
- [x] Windows release is built as a GUI subsystem app; no console window is requested by the release binary.

## Explicitly out of scope
Background file movement, scheduled file movement, automatic deletion, cloud file-content upload, and silent overwrite are not part of V0.4.

## Current verification status

RC5 Windows checkpoint requested on 2026-09-26 after the approved-path and Windows canonical-containment fixes. CI now guards the Windows GUI subsystem directive and package/Tauri version alignment. A Windows installer is intentionally built only at explicit checkpoints, not on every source change.
Latest complete green baseline: commit `277046459a5ada57016af820eb8e45531ea366e3`, CI run `36212281162` and Web Preview run `36212281147`, both passed on 2026-09-26. Current V0.4 invalidates Move validation whenever review/classification state or a Downloads scan changes, binds final execution to the exact validated source-target pairs, rejects overlapping Work/Downloads roots in both UI and Rust, keeps failed Undo transactions retryable in the desktop UI, and regression-tests destination-collision immutability. Downloads routing now uses only approved existing Folder Map paths; ambiguous multi-folder roles are held instead of creating a synthetic role directory. Primary navigation modes are mutually exclusive, and Windows target containment uses canonical parent validation. Source-verifiable V0.4 acceptance items are closed; destructive/background behavior remains explicitly out of scope. Routine source changes are covered by automated CI and do not require repetitive manual testing.
