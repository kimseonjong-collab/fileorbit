# FileOrbit V0.4 Acceptance

## Release gate
V0.4 is acceptable for a Windows checkpoint build only when all items below pass.

### Folder Doctor / Folder Map
- [x] Existing work root is selected explicitly by the user. (desktop folder dialog; Work Root is separate from Downloads Root)
- [x] Folder scan is read-only. (backend scan path performs metadata/read traversal only; no mutation calls)
- [x] Noise exclusions do not mutate disk content. (excluded directories are skipped by WalkDir filter only)
- [x] Folder Map is persisted only after explicit approval. (`fileorbit.folderMap.v02` is written by the explicit approval action)
- [x] Drift between saved Folder Map sources and a later scan is visible. (saved/current source sets show added/missing counts)

### Downloads Organizer
- [x] Downloads root is selected explicitly. (desktop UI keeps Downloads selection separate from Folder Map work root; UI and Rust reject either root being equal to or nested inside the other)
- [x] Scanning does not move, rename, delete, or overwrite files. (`scan_downloads` reads directory entries/metadata only)
- [x] Recommendation, review, and hold states are distinguishable. (separate counts, filters, status labels, and confidence treatment)
- [x] Manual classification correction is stored locally. (role overrides + learned filename tokens persist locally and are scoped to the approved map)
- [x] Per-file review decisions and overrides are scoped to Folder Map approval version + Folder Map root + Downloads root. Re-approving a Folder Map invalidates prior approvals so a changed destination map cannot inherit stale Move approval.
- [x] Re-scan retains decisions only for files still present. (scan reconciliation prunes stale decision/override keys)
- [x] Downloads recommendations route only to an actually approved Folder Map source folder. A role with multiple approved source folders is held for review instead of synthesizing a new destination directory.

### Move safety
- [x] Move requires approved Folder Map. (UI gate + backend approved-root validation)
- [x] Move requires explicit per-file approval and final Move confirmation. (desktop Move Gate; changing approval/classification or re-scanning invalidates the prior validation/armed state)
- [x] Rust validates source under selected Downloads root. (preflight + execution-time canonical-path guard)
- [x] Rust validates target under approved work root using the canonicalized existing target parent. This avoids Windows `\\?\\C:\\...` canonical-prefix false negatives while retaining symlink/escape containment.
- [x] Parent-directory traversal and invalid relative path elements are rejected. (backend guard + Rust unit test)
- [x] Existing destination collision is rejected; overwrite is never silent. (preflight immutability regression + move primitive guard)
- [x] Duplicate source or duplicate target entries in one Move plan are rejected before execution. Source identity is canonicalized; Windows duplicate comparison is case-insensitive.
- [x] Same-volume move is journaled. (`planned` then `moved`/`failed` entries are appended around execution)
- [x] Cross-volume fallback uses temporary copy + byte-size verification before source removal. (forced fallback Rust unit test)
- [x] Failed cross-volume source removal attempts rollback of the created destination. (fallback implementation removes created target if source removal fails; controlled failure injection remains optional)

### Journal / Undo
- [x] Planned, moved, failed, undone, and undo_failed states are auditable in the JSONL journal; execution-time Move failures are journaled after `planned`.
- [x] Move history is persisted in the app-data JSONL journal and reloaded after restart; each appended record is flushed with `sync_data` before it is treated as committed.
- [x] Undo availability is derived from the latest successful moved/undone state per source.
- [x] Undo collision stops that item rather than overwriting the original path. (undo precheck Rust unit test)
- [x] Failed Undo remains retryable after the external cause is resolved. (backend state remains undoable and desktop UI retains the failed last transaction for retry)
- [x] Empty, unknown, or fully exhausted Undo transactions do not report a false success; backend returns an explicit error.
- [x] Transaction detail exposes source, target, status, and error.
- [x] Journal reader rejects malformed interior records and unknown states instead of silently skipping corruption; only a truncated final record (possible interrupted append) is tolerated. Covered by Rust regression tests.
- [x] Partial Undo state is source-scoped: `undo_failed` remains retryable, already `undone` sources stay completed, and planned/failed journal noise cannot consume a successful moved state. History and Undo execution share the same eligibility reducer.
- [x] Interrupted journal append recovery is deterministic: a malformed final partial record is ignored for reads and physically truncated before the next append; a complete final JSON record without a trailing newline is preserved. Regression tests cover both boundaries.
- [x] History aggregation is deterministic and single-pass over journal entries: counts, latest timestamp, partial-Undo eligibility, and equal-timestamp ordering are regression-tested. No automatic journal deletion/compaction is performed in V0.4.
- [x] Move and Undo both require the live source to be a regular file at their final safety boundary; a directory or other non-file path cannot pass merely because it is inside an approved root. Regression tests preserve the no-touch behavior.
- [x] Approved Downloads Move plans carry the scanned source size and modified timestamp. Backend validation and execution-time revalidation both reject a source whose snapshot changed after review, reducing validation-to-move TOCTOU risk without hashing file contents.
- [x] Source modified timestamps use the same Unix-millisecond precision in Downloads scan and backend snapshot revalidation, avoiding precision mismatch while retaining change detection.
- [x] All direct npm dependency and devDependency versions are exactly pinned and CI rejects floating ranges. A repository lockfile is still a follow-up before switching workflows from `npm install` to `npm ci`; current workflows intentionally remain install-based until that artifact exists.
- [x] Rust dependency baselines are explicitly versioned and CI reports whether `src-tauri/Cargo.lock` is present. V0.4 does not claim fully reproducible transitive Rust resolution until that lockfile is committed; cargo check/test remain mandatory gates.
- [x] History aggregation is regression-tested with a 15,000-entry in-memory journal (200 transactions × 75 records), preserving counts, newest-first ordering, and partial-Undo retryability without timing-based/flaky assertions.
- [x] Planned-only transactions remain visible as interrupted history instead of appearing as an ambiguous zero-result transaction; they are never Undo-enabled.
- [x] Transaction detail preserves physical journal append order. Equal-millisecond `planned → moved/failed` records are not re-sorted, so the audit sequence remains faithful to the persisted JSONL order.
- [x] History exposes read-only journal diagnostics (bytes and valid record count). At 10 MiB or 50,000 records it shows a growth warning only; V0.4 never auto-deletes or auto-compacts audit history.
- [x] Journal diagnostics fail closed on interior corruption by reusing the strict journal reader; corrupted history is not silently reported as healthy statistics.
- [x] New journal appends fail closed when an interior record is corrupted and leave the journal byte-for-byte unchanged. Move execution preflights audit integrity before any file mutation, while a malformed truncated final tail remains recoverable by the established tail-repair rule.
- [x] Undo performs the same journal tail recovery + strict integrity read before restoring any file.
- [x] After a physical Move succeeds, failure to persist the `moved` audit record triggers an immediate compensating move back to the original source. If that compensation also fails, the returned error reports both journal and rollback failures instead of claiming success.

## Explicitly out of scope
Background file movement, scheduled file movement, automatic deletion, cloud file-content upload, and silent overwrite are not part of V0.4.

## Current verification status

RC5 Windows checkpoint requested on 2026-09-26 after the approved-path and Windows canonical-containment fixes. CI now guards the Windows GUI subsystem directive and package/Tauri version alignment. A Windows installer is intentionally built only at explicit checkpoints, not on every source change.
Windows runtime acceptance passed on 2026-09-26 with RC5: an approved two-file plan validated 2/2, moved 2 with 0 failures, journaled PLANNED→MOVED, undid 2 with 0 Undo failures, and the transaction plus Folder Map SAVED state persisted after a full app restart. Latest source hardening baseline adds strict journal-corruption handling and CI guards for the desktop Vite base and validate-before-confirm Move gate ordering. Current V0.4 invalidates Move validation whenever review/classification state or a Downloads scan changes, binds final execution to the exact validated source-target pairs, rejects overlapping Work/Downloads roots in both UI and Rust, keeps failed Undo transactions retryable in the desktop UI, and regression-tests destination-collision immutability. Downloads routing now uses only approved existing Folder Map paths; ambiguous multi-folder roles are held instead of creating a synthetic role directory. Primary navigation modes are mutually exclusive, and Windows target containment uses canonical parent validation. Source-verifiable V0.4 acceptance items are closed; destructive/background behavior remains explicitly out of scope. Routine source changes are covered by automated CI and do not require repetitive manual testing.
